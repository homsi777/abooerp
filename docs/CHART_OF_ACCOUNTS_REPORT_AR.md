## 0. تحديث — دعم التسلسل الهرمي (تجميعي/حركي)

أُضيف لاحقاً دعم **حسابات تجميعية (Group, `is_postable=false`)** مقابل **حسابات حركية (Posting, `is_postable=true`)** بعمق غير محدود (حتى 6 مستويات)، عبر الهجرة [`136_chart_of_accounts_hierarchy.sql`](../server/src/db/migrations/136_chart_of_accounts_hierarchy.sql). التغييرات الجوهرية على ما ورد أدناه:

- عمود جديد `is_postable` على `chart_of_accounts` — الحساب التجميعي **لا يمكن ترحيل قيود عليه مباشرة** (قيد trigger في قاعدة البيانات).
- زُرعت **5 حسابات تجميعية** جديدة (1000 الأصول، 1400 الذمم المدينة، 2000 الخصوم، 4000 الإيرادات، 5000 المصاريف) وأُعيد تنظيم الحسابات الأصلية الـ14 تحتها — **صار المجموع 19 حساباً** بدل 14.
- إضافة حساب فرعي تحت أي حساب حركي يحوّله تلقائياً لتجميعي (إن لم يكن عليه قيود بعد).
- **تصحيح مهم لِما ورد في القسم 7 أدناه**: تبيّن عند تدقيق أعمق أن نظام فتح/إغلاق ورديات العهدة (custody shifts) **يُرحِّل فعلياً** قيوداً تلقائية حقيقية على حسابي 1100 (الصندوق الرئيسي) و1300 (عهد الورديات والسلف) عبر `financeRepository.ts`‎ — فـ"القيد اليدوي" ليس العملية الآلية الوحيدة الموجودة كما ذُكر سابقاً. كلا الحسابين يبقيان حركيين (postable) دائماً ضمن إعادة التنظيم الجديدة، فلا تعارض.
- تفاصيل كاملة (قواعد الإنشاء/التعديل، اقتراح الرمز التالي، نقاط API الجديدة) موثَّقة في القسم 9 الجديد أدناه.

## 1. نظرة عامة

شجرة الحسابات هي دليل الحسابات المحاسبي للشركة — القائمة الهرمية لكل بنود الأصول والخصوم وحقوق الملكية والإيرادات والمصاريف التي يمكن تسجيل حركات مالية عليها. أُضيفت كميزة إدارية مستقلة تتيح لأي مستخدم بصلاحية مالية مناسبة إضافة أو تعديل أو إلغاء تفعيل أي بند حساب، بنفس أسلوب برامج المحاسبة التقليدية (مثال: إضافة "مسحوبات الشركاء" كحساب فرعي تحت "حقوق الملكية").

**أين تجدينها:** قسم **المالية** ← بطاقة **"🌳 شجرة الحسابات"** (بجانب بطاقة "دفتر الأستاذ")
**المسار المباشر:** `/finance/chart-of-accounts`
**الملف المصدري:** [`src/pages/finance/ChartOfAccounts.tsx`](../src/pages/finance/ChartOfAccounts.tsx)

## 2. البنية في قاعدة البيانات

الجدول الأساسي `chart_of_accounts` (أُنشئ في الهجرة [`121_accounting_foundation.sql`](../server/src/db/migrations/121_accounting_foundation.sql)):

| العمود | النوع | الوصف |
|---|---|---|
| `id` | uuid | المعرّف الفريد |
| `company_id` | uuid | الشركة المالكة للحساب (عزل متعدد الشركات) |
| `account_code` | text | رمز الحساب — فريد لكل شركة، **لا يمكن تعديله بعد الإنشاء** |
| `account_name` | text | اسم الحساب — قابل للتعديل دائماً |
| `account_type` | text | أحد: `asset` (أصول) / `liability` (خصوم) / `equity` (حقوق ملكية) / `revenue` (إيرادات) / `expense` (مصاريف) — **ثابت بعد الإنشاء** |
| `normal_balance` | text | `debit` (مدين) أو `credit` (دائن) — **ثابت بعد الإنشاء** |
| `parent_account_id` | uuid | الحساب الأب (لبناء الشجرة) — قابل للتغيير |
| `is_control_account` | boolean | هل هو "حساب تحكّم" مرتبط بأطراف خارجية (عملاء/وكلاء...) بدل حساب فردي |
| `control_party_type` | text | نوع الطرف إن كان حساب تحكّم: `customer` / `agent` / `sender_receiver` / `supplier` |
| `is_active` | boolean | نشط/غير نشط — الإلغاء دائماً "إلغاء تفعيل" وليس حذفاً فعلياً |
| `notes` | text | ملاحظات حرة اختيارية |

**قيد فريد:** `(company_id, account_code)` — لا يمكن تكرار نفس الرمز داخل نفس الشركة.

### جدولان مرتبطان (مُجهَّزان، لكن غير مُفعَّلين تلقائياً بعد — انظر القسم 6)

- **`journal_entries`** — القيود اليومية (رقم القيد، التاريخ، الوصف، نوع المصدر، حالة: مسودة/مرحَّل/معكوس).
- **`journal_entry_lines`** — بنود كل قيد (حساب، مبلغ مدين أو دائن حصراً، عملة وسعر صرف، طرف مرتبط اختياري). محمي بـ **trigger** يرفض أي قيد غير متوازن (مجموع المدين ≠ مجموع الدائن) عند الـ commit.

## 4. مفهوم "حساب التحكّم" (Control Account) — مهم

لاحظي أن حسابات مثل "ذمم العملاء" أو "ذمم الوكلاء" هي حساب **واحد إجمالي** لكل فئة، وليس حساباً منفصلاً لكل عميل/وكيل على حدة. رصيد كل عميل أو وكيل فردي يُتبَّع من خلال حقلي `party_type`/`party_id` داخل بنود القيود (`journal_entry_lines`)، وليس عبر إنشاء حساب مستقل لكل طرف. هذا يعني:

- ❌ لا تُنشئي حساباً منفصلاً لكل عميل أو وكيل جديد — استخدمي حساب التحكّم الموجود (1410، 1420...).
- ✅ الشجرة مخصَّصة لبنود الحسابات العامة فقط (نثريات، مصاريف، حسابات شركاء، بنود جديدة من النوع الذي اقترحه المدير مثل "مسحوبات الشركاء").

## 5. كيف تعمل الشاشة فعلياً

### العرض (يمين الشاشة)
شجرة هرمية قابلة للطي/التوسيع، مرتّبة أبجدياً برمز الحساب. كل سطر يعرض: الرمز، الاسم، نوع الحساب (شارة ملوّنة)، الطبيعة (مدين/دائن)، وثلاثة أزرار إجراء:
- **⊕** إضافة حساب فرعي تحت هذا الحساب مباشرة
- **✏️** تعديل (الاسم، الحساب الأب، الملاحظات فقط)
- **حذف** (يعني إلغاء تفعيل — غير ظاهر لحسابات التحكّم المحمية)

### النموذج (يسار الشاشة)
عند الإنشاء: رمز + اسم + نوع + طبيعة (تُملأ تلقائياً حسب النوع المختار، قابلة للتعديل) + حساب أب اختياري + ملاحظات.
عند التعديل: الرمز والنوع والطبيعة تُعرَض **معطّلة** (رمادية، غير قابلة للتغيير) — فقط الاسم والحساب الأب والملاحظات قابلة للتعديل.

### قيود منطقية مفروضة من الخادم
1. **رمز الحساب لا يتكرر** داخل نفس الشركة (قيد قاعدة بيانات).
2. **النوع والطبيعة المحاسبية لا يمكن تغييرهما بعد الإنشاء** — فقط عبر إعادة الإنشاء بحساب جديد.
3. **لا يمكن إلغاء تفعيل حساب له حسابات فرعية نشطة** — يجب إلغاء تفعيل الفروع أولاً (رسالة خطأ واضحة: "يحتوي هذا الحساب على حسابات فرعية — ألغي تفعيلها أولاً").
4. **لا حذف فعلي أبداً** — فقط `is_active = false`، حفاظاً على أي قيود تاريخية مرتبطة بالحساب مستقبلاً.

## 7. ما هو خارج النطاق حالياً — ملاحظة مهمة

رغم وجود بنية القيود اليومية (`journal_entries` / `journal_entry_lines`) كاملة في قاعدة البيانات، **لا يوجد حالياً أي ربط تلقائي** بين سندات القبض/الدفع الفعلية (`receipt_vouchers` / `payment_vouchers`) أو حركات المحافظ وبين هذه القيود. بمعنى آخر:

- شجرة الحسابات اليوم هي **دليل حسابات مستقل قائم بذاته** — تضيفين وتعدّلين بنوده، لكنه لا "يتحرك" تلقائياً مع كل سند تُنشَأ فعلياً في النظام.
- إضافة الترحيل التلقائي (auto-posting) من السندات إلى القيود اليومية كانت **خارج نطاق** التأسيس الأول عمداً (موثَّق صراحة في تعليق الهجرة 121)، وتحتاج موافقة وخطوة منفصلة لاحقة.
- لا توجد حالياً شاشة لإدخال "قيد يدوي" (manual journal entry) من الواجهة رغم أن الـ API الخلفي (`/journal-entries`) موجود جزئياً في `financeRoutes.ts`.

**الخلاصة العملية:** شجرة الحسابات اليوم أداة تنظيمية/تحضيرية ممتازة لتهيئة دليل الحسابات بالشكل الصحيح — لكنها ليست بعد محاسبة مزدوجة القيد فعلية تعمل تلقائياً مع باقي النظام.

## 8. توصيات للخطوة التالية (اختيارية — لم تُنفَّذ بعد)

1. **شاشة "قيد يدوي"** في الواجهة لاستخدام `journal_entries`/`journal_entry_lines` الموجودة فعلاً في الخادم.
2. **ربط تلقائي** بين سندات القبض/الدفع الحالية وبين القيود اليومية (نقطة قرار محاسبية مهمة تحتاج مراجعة منفصلة مع المحاسب قبل التنفيذ).
3. **تقرير ميزان المراجعة** (Trial Balance) يعتمد على `chart_of_accounts` + `journal_entry_lines` مجمَّعة — غير موجود بعد.

## 9. الدعم الهرمي — تفاصيل كاملة (مُضاف 2026-10-26)

### 9.1 عمود `is_postable` وقواعد تحويل التصنيف
| القاعدة | الوصف |
|---|---|
| حساب جديد بدون أب | `is_postable` يُحدَّد صراحة من المستخدم (افتراضياً حركي) |
| حساب جديد تحت أب حركي | الأب يتحوّل تلقائياً لتجميعي **فقط إن لم يكن عليه أي قيد** — وإلا 409 |
| حساب جديد تحت أب تجميعي بالفعل | يُسمح مباشرة، الأب يبقى كما هو |
| حساب جديد تحت حساب تحكّم أو عمقه ≥ 6 | مرفوض (409 / 400) |
| تحويل حساب حركي → تجميعي يدوياً | مرفوض إن كان عليه أي قيد |
| تحويل حساب تجميعي → حركي يدوياً | مرفوض إن كان له فروع نشطة |
| حساب تحكّم (`is_control_account`) | لا يمكن أن يصبح تجميعياً أبداً (قيد قاعدة بيانات `chk_control_is_postable`)، ولا يمكن استخدامه كأب لحساب جديد |

### 9.2 الوراثة عند الإنشاء تحت أب
نوع الحساب (`account_type`) وطبيعته (`normal_balance`) **يُوَرَّثان دائماً من الأب** ويُتجاهَل أي قيمة مختلفة يرسلها العميل — القيمتان مطلوبتان فقط عند إنشاء حساب رئيسي (بلا أب).

### 9.3 حماية الدورة (Cycle) وتطابق النوع عند تغيير الأب
عند تعديل `parent_account_id` لحساب موجود:
- يُرفَض لو كان الأب الجديد أحد فروع الحساب نفسه (أو الحساب نفسه) — 409.
- يُرفَض لو كان الأب الجديد من نوع محاسبي مختلف — 409.
- الحد الأقصى للعمق: **6 مستويات**.

### 9.4 اقتراح الرمز التالي — نقطة API جديدة
`GET /chart-of-accounts/:id/next-code` (حيث `:id` هو **الحساب الأب**) → `{ "code": "3200" }`. معادلة الخطوة: 100 إن كان رمز الأب من مضاعفات 1000، وإلا 10 إن كان من مضاعفات 100، وإلا 1 — مع تفادي أي تصادم مع رمز موجود فعلاً.

### 9.5 نقاط API المتأثرة
| النقطة | التغيير |
|---|---|
| `GET /chart-of-accounts` | أضيف `is_postable`، `is_active`، `children_count` لكل سطر |
| `POST /chart-of-accounts` | `accountType`/`normalBalance` صارا اختياريين (موروثان عند وجود أب)، أضيف `isPostable`، رمز الحساب الآن أرقام فقط (3–10 خانات) |
| `PUT /chart-of-accounts/:id` | أضيف `isPostable` اختياري (بلا تغيير تصنيف إن لم يُرسَل)؛ تغيير الأب الآن يخضع لفحص الدورة وتطابق النوع |
| `GET /chart-of-accounts/:id/next-code` | **جديد بالكامل** |
| `POST /journal-entries` | يرفض الآن بخطأ 409 واضح `لا يمكن ترحيل قيد على حساب تجميعي` بدل تسريب خطأ 500 خام عند استهداف حساب تجميعي |

### 9.7 التحقق الفعلي (ليس توقعاً نظرياً)
جُرِّبت جميع القواعد أعلاه فعلياً عبر استدعاءات API حقيقية على قاعدة التطوير المحلية (تسجيل دخول admin حقيقي، إنشاء/تعديل/رفض حسابات، محاولة ترحيل قيد على حساب تجميعي، اختبار العمق حتى المستوى السابع) — كلها أعطت النتيجة المتوقعة بالضبط. الهجرة أُعيد تطبيقها يدوياً مرتين للتأكد من عدم التكرار (idempotent) بنجاح.
